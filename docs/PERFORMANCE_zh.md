## 1. 现行加速项

只剩 **5 个开关 + 3 个参数**。开关与 `web/app.js` 的 `CFG_KEYS` 一一对应：`fp16` `s2mel_fp16` `w2v_fp16` `qwen_fp16` `cudnn_benchmark`。

| 项 | 类别 | 生效条件 | 实测效果 | 代价 |
|---|---|---|---|---|
| `fp16`（GPT 主模型半精度） | 需 GPU，跨厂商 | CUDA / Intel XPU；**MPS 与 CPU 被代码自动关闭** | 显存减半、推理更快 | 几乎无损 |
| `s2mel_fp16`（扩散半精度） | 需 GPU，跨厂商 | CUDA / XPU / MPS | 长 180 字 **-32%**（75.8s → 51.4s） | 音质略变 |
| `w2v_fp16`（w2v-bert 语义编码器半精度） | 需 GPU，跨厂商 | CUDA / XPU；默认**开** | **省约 1GB 显存**，8GB 卡单项最大节约 | 需自测音色与可懂度 |
| `qwen_fp16`（Qwen 情感模型半精度） | 需 GPU，跨厂商 | CUDA / XPU；默认**开** | 该模型本就以 float16 加载，此项把现状显式化 | 关闭可回退 FP32 排查音质 |
| `cudnn_benchmark` | NVIDIA 专属 | 任意 NVIDIA GPU | **负优化：BigVGAN 3.35s → 97.24s** | 无收益，保持关闭 |
| `diffusion_steps` | 完全通用 | 任何设备 | 25 → 10 时 s2mel 31.2s → 10.5s | 音质略变（建议 8~16） |
| `inference_cfg_rate` | 完全通用 | 任何设备 | 0.7 → 0 约省一半 s2mel 时间 | 参考音频风格跟随弱化 |
| `max_text_tokens_per_segment` | 完全通用 | 任何设备 | 段数减少即减少每段固定开销 | 需与 `max_mel_tokens` 联动防截断 |
| `gpt_batch_size`（段级批处理，2026-10-30 新增） | 完全通用 | 非流式（`stream_return=False`）+ 多段文本；**默认 0 = 关闭** | b=3 时**每行每 token 成本 13.82 → 5.47 ms（2.6×）** | 见 §6：流式路径不启用，首包不受影响 |

**设备自动降级**：唯一逻辑在 `indextts/infer_v2.py` 的设备分支 —— CPU 自动关 `fp16`，MPS 也自动关（MPS 上 fp16 反而更慢），无需人工干预。

## 2. 已移除的 5 项（2026-09-11）

都因为**绑定特定厂商/平台，且在本项目实测中无收益甚至负优化**，已整体删除（覆盖 12 个文件，含 `indextts/accel/` 整包约 1200 行、5 个 CLI 参数与前端开关）。

| 项 | 原绑定 | 移除原因（实测） |
|---|---|---|
| `tf32` | NVIDIA，且 Ampere 及以上（cc≥8.0） | 代码无架构检测，Turing 及更早的卡上**静默无效** |
| `cuda_kernel` | NVIDIA + 本地编译 CUDA 扩展 | BigVGAN 修完 no_grad 后收益可忽略，却要长期维护编译 |
| `accel`（flash-attn） | Ampere 系 | 8GB 卡**反向加速**：关掉后短 50 字 344.5s→16.6s（-95%）、长 180 字 174.6s→75.8s（-57%） |
| `torch_compile` | 需 Triton | 编译缓存后长文本仍 ~890s（慢 5 倍），首次还要现场编译 1~2 分钟 |
| `deepspeed` | 仅 Linux | Windows 构建链依赖 Linux 专属组件，单卡收益本就有限 |

**保留未动**：vendored 第三方库自带的 `use_cuda_kernel` 参数（项目不再传值即走默认 False；删它属于破坏库完整性）、`transformers_*.py` 里的 `deepspeed` 引用（框架自身的多卡训练支持）。

## 3. 实测数据

测试文本：短 12 字 / 短 50 字 / 长 180 字；参考音频 `examples/voice_05.wav`，`emo_mode=0`；生成参数 WebUI 默认（`num_beams=3`、`top_p=0.8`、`top_k=30`、`max_mel_tokens=1500`、`max_text_tokens_per_segment=120`）。计时口径为 `POST /tts` SSE 的 `done.elapsed`（含排队、不含首次模型加载），每轮先跑「你好。」预热。

### 3.1 BigVGAN 补 `no_grad()`：收益最大的单项

漏包 `with torch.no_grad():` 让它以训练模式裸跑，占整条链路 85% 的时间。

| 指标 | 修复前 | 修复后 |
|---|---|---|
| BigVGAN 单步 | 128.0s | **0.33s**（约 388x） |
| 整段（实测同一次请求） | 151s / 12.77s 音频 | **6.3s / 4.78s 音频** |
| RTF（实测同一次请求） | 11.87 | **1.31** |
| 整段（折算到 12.77s 音频） | 151s | **约 16.7s（12.77 × 1.31）** |

修复前后两次生成的音频长度不同（`do_sample=True`，停点随机），所以同长度耗时按 RTF 折算：**约 9 倍**
（151/16.7 ≈ 11.87/1.31 ≈ 9.0）。不能拿 151s 直接除以 6.3s（24 倍，分母音频长度不同）；旧文档写的
「~21s / 7 倍」无法由这两组数据复现，已按实测 RTF 统一口径修正。

### 3.2 `accel`（flash-attn）打开即灾难

| 文本 | accel ON | accel OFF | 差异 |
|---|---|---|---|
| 短 12 字 | 112s（更长文本 280s 未跑完，卡在 gpt 段） | **9.2s** | -92% 以上 |
| 短 50 字 | 344.5s | **16.6s** | -95% |
| 长 180 字 | 174.6s | **75.8s** | -57% |

表现为 GPU 满载但自回归 decode 每步极慢：8GB 专用显存跑满后触发共享内存换页，kernel 反复走 PCIe。

### 3.3 `torch_compile`（长 180 字，accel 仍 ON）

| 状态 | 耗时 |
|---|---|
| 关闭 | 174.6s（参照） |
| 开启第 1 次（含 ~3 分钟 Triton 编译） | 356.3s |
| 开启第 2 次（编译缓存后） | **~890s（≈15min）**，专用显存峰值 7993 MiB |

编译图额外占显存，长文本多段激活持续换页 → 稳定态反而慢 5 倍。

### 3.4 即开即生效项

长 180 字（accel OFF 基线）：

| 配置 | 耗时 | 相对基线 |
|---|---|---|
| 基线（25 步 / CFG 0.7 / fp32 s2mel） | **75.8s** | — |
| `diffusion_steps=12` | 72.0s | -5% |
| `inference_cfg_rate=0` | 61.9s | -18% |
| **`s2mel_fp16=ON`** | **51.4s** | **-32%** |

短 50 字下这些项的差异都在噪声范围内（16.6s ± 2.5s），真实收益只看长文本。

### 3.5 `cudnn_benchmark` 是负优化（2026-09-11 纠正）

| 阶段 | `False` | `True` |
|---|---|---|
| gpt_gen | 9.34s | 10.80s |
| s2mel | 23.88s | 31.23s |
| **bigvgan** | **3.35s** | **97.24s** |
| 整段 | **37.95s**（RTF 6.12） | **141.44s**（RTF 20.79） |

根因：`benchmark=True` 会在**每次遇到新输入尺寸**时对所有候选卷积算法跑一遍基准再挑最快的；TTS 每次生成音频长度都不同 → 几乎每次推理都在重新搜索。原结论「预热后更快」只对固定输入尺寸（定长批处理）成立。

### 3.6 显存口径（8GB 卡）

| 指标 | 实测 |
|---|---|
| 模型加载后专用显存（闲置） | 7860 ~ 7895 MiB / 8192 |
| 推理峰值专用显存 | 7968 ~ 7993 MiB |
| 常驻共享 GPU 内存 | **~1640 MiB**（稳定，与是否生成无关） |

全家权重常驻（w2v-bert-2.0 + GPT fp16 + s2mel fp32 + codec/bigvgan + campplus + qwen-0.6b）超过 8GB 专用预算，WDDM 自动把 ~1.6GB 放到共享系统内存 —— **这是常态，不是 bug**。危险点是生成长文本多段 + 3 beam + 25 步双路 CFG 时的换页叠加。

## 4. 8GB 卡推荐配置

```
fp16=1  s2mel_fp16=1  w2v_fp16=1  qwen_fp16=1  cudnn_benchmark=0
diffusion_steps=25  inference_cfg_rate=0.7
```

四项 fp16 在 `server.py` 的 argparse 里默认全开，`start_server.bat` 只暴露 `CUDNN_BENCHMARK` / `DIFFUSION_STEPS` / `CFG_RATE`，其余可在「模型管理」页在线切换（即时生效，无需重启）。唯一有明显音质取舍的是 `s2mel_fp16`（-32% 时间），介意听感可关掉，其余三项基本无损。

| 设备 | 建议开启 | 不要开 |
|---|---|---|
| NVIDIA Ampere+（含 8GB） | 四项 fp16 全开（默认）；`diffusion_steps` 按听感调 10~16 | `cudnn_benchmark` |
| NVIDIA Turing / 更早 | 同上 | `cudnn_benchmark` |
| AMD（ROCm）/ Intel XPU | 同上 | `cudnn_benchmark` |
| Apple MPS | 只开 `s2mel_fp16`（`fp16` 代码自动关） | `cudnn_benchmark` |
| 纯 CPU | 只调 `diffusion_steps` / `cfg_rate` / 分段参数 | 所有 GPU 项 |

显存吃紧（撞 OOM）时先确认 `w2v_fp16` 开着 —— 单项收益最大（~1GB）。

**请求卡死（>5 分钟无响应）的恢复**：进程内 `/model/restart` 无法中断卡死的孤儿推理（`_INFER_LOCK` 串行），只能重启进程：

```powershell
Get-NetTCPConnection -LocalPort 7860 | ForEach-Object { Stop-Process -Id $_.OwningProcess -Force }
# 再执行 start_server.bat
```

## 5. 解码步剖析（2026-10-30 新增，纠正了此前两个猜测）

`kv_cache` 一直是开着的（`indextts/infer_v2.py:100` 传 `kv_cache=True`），所以 gpt 解码**不存在** O(L²) 重算问题。下面是一次实测澄清，脚本：`tools/profile_gpt_decode.py`、`tools/profile_step_ops.py`、`tools/bench_batch_scale.py`、`tools/probe_gpt_batch.py`、`tools/verify_batch_codes.py`。

### 5.1 每步 KV 拼接拷贝只占 ~1%（不是瓶颈）

单行、fp16、`beams=3`、连续 1400 个解码步，按 cache 长度分桶平均：

| cache 长度 L | 50 | 200 | 400 | 600 | 800 | 1000 | 1200 | 1400 |
|---|---|---|---|---|---|---|---|---|
| ms/步 | 13.03 | 11.11 | 10.48 | 10.99 | 10.56 | 10.43 | 10.71 | 12.87 |
| 理论 cat 拷贝量 | 6.1 MB | 24 MB | 49 MB | 74 MB | 98 MB | 123 MB | 147 MB | 172 MB |

步耗时与 L 基本无关（prefill 34.9 ms）。按 300 GB/s 的保守带宽，L=1400 时的拼接待拷贝也只有 0.57 ms。`torch.profiler` 直接给出同一个结论：`aten::cat` 每步 0.18 ms，占 13.8 ms 的 **1.3%**。

**→ "静态 KV cache 省掉每步拼接 = 大幅加速"这个前提不成立。** 静态 cache 单独只值 ~1%，它的价值只在于"形状固定"（CUDA graph 的前提）。

⚠️ 但**只在单行时成立**。批处理会把每步拷贝量乘上行数×beam 数：`12 行 beam × 1500 token` 每步要 cat 2.16 GB，那时拷贝就成了主导（§6.2 实测慢 8 倍），所以静态 cache 在批处理路径上又变得有意义。

### 5.2 真瓶颈是每步的 CPU 提交（GPU 只忙 1/3）

20 个解码步的 profiler 汇总（1 行，fp16）：

| 指标 | 每步 |
|---|---|
| Self CUDA 时间 | **4.6 ms** |
| Self CPU 时间 | **15.3 ms** |
| 墙钟 | 13.8 ms（CPU 与 GPU 部分重叠） |
| `cudaLaunchKernel` 次数 | **625 次**（5.9 µs/次 ≈ 3.7 ms CPU） |
| `aten::addmm` 次数 | **169 次**（self CPU 42 µs × 169 ≈ 2.8 ms） |
| `aten::to` / `_to_copy` | 198 次 |

主要 GPU 内核：cutlass f16 gemm 30.5 ms/20、ampere_fp16_s16816gemm 22.6 ms/20、fmha_cutlass（SDPA efficient attention）5.4 ms/20、layer_norm 3.8 ms/20。

**→ b=1 的解码是"CPU 排队喂 GPU"，GPU 有 2/3 时间是闲的。** 所以要么**把多行塞进同一个 batch**（下面的段级批处理，立刻见效），要么**把 CPU 提交次数降下来**（CUDA graph / 算子融合，属于后续方向，见 §7）。

### 5.3 `beams 3→1` 只有 ~12%，别当大杠杆

因为每步开销主要是"提交 625 个 kernel"，与行数几乎无关：少 2 行 beam 只省 GPU 计算那 4.6 ms 里的 attention 部分。`archive/OPTIMIZATION_HANDOFF.md` 里"减 3 倍候选池 → gpt_gen 4s→1.5s"的估算过于乐观，实测只有 ~12%。要提速应减少**每步提交**，而不是减少**行数**。

### 5.4 `_reorder_cache` 疑点：运行时已证伪

交接文档怀疑 `GPT2InferenceModel` 没有 `_reorder_cache`、beam search 下 KV cache 没被重排。实际：

- 定义在 `indextts/gpt/model_v2.py:199-212`（`@staticmethod`，按 `beam_idx` 做 `index_select`）。
- 本项目用的是 fork 的生成实现（`indextts/gpt/transformers_generation_utils.py:3299` 的 `_temporary_reorder_cache`），`_supports_cache_class=False` → 走 legacy tuple 分支 → 调 `self._reorder_cache`。
- 探针实测：每个解码步调用 1 次（3 段共 408 次），实现为 `GPT2InferenceModel._reorder_cache`；把 `_reorder_cache` 换成恒等函数后输出直接变了（107 vs 98 步，第 0 步就开始分叉）→ 它在真正工作，不是死代码。

**→ 没有正确性 bug；`beams 3→1 只快 12%` 这个测量本身是可信的。**

### 5.5 批处理在数学上等价（fp32 逐 token 相同）

同 3 段文本（13 / 43 / 120 个 text token）：

| 配置 | 逐段 vs 批处理 |
|---|---|
| fp32 | **三段 mel codes 全部逐 token 相同**，prefill 末位 logits max\|diff\| = 1e-5 |
| fp16 | 2/3 段相同；最短段第 48 步起分叉（beam 平票被数值噪声翻转） |

fp16 的分叉来自不同 batch 形状触发了不同的 cuDNN/cuBLAS 内核，是数值噪声而非结构性耦合。另外生产默认 `do_sample=True`，每次生成本来就是随机采样，因此批处理不会带来"可听出来的质量差异"（要做严格 A/B 请用 `--fp32`）。

## 6. 已实施：段级批处理（`gpt_batch_size`）

非流式路径上，把多段文本拼成一个 batch 只调一次 `gpt.inference_speech`，再按行切回各段的 mel code。实现：`IndexTTS2._precompute_segment_codes`（`indextts/infer_v2.py`）。

单步成本微基准（固定文本、单配置独立进程、`beams=3`、RTX 3060 Ti 8GB）：

| 配置 | `max_mel` | 生成 token | 耗时 | ms/token | **ms/行token** | 显存峰值 |
|---|---|---|---|---|---|---|
| b=1 | 300 | 107 | 1479 ms | 13.82 | 13.82 | 1.96 GiB |
| b=2 | 300 | 279 | 4368 ms | 15.65 | **7.83** | 2.56 GiB |
| b=3 | 300 | 281 | 4609 ms | 16.40 | **5.47** | 2.90 GiB |
| b=1 | 100 | 100 | 1438 ms | 14.38 | 14.38 | — |
| b=3 | 100 | 100 | 1659 ms | 16.59 | **5.53** | 2.34 GiB |

**每多一行只多 ~1~2 ms/token**（GPU 有富余），所以行数越多越划算，直到显存撞墙（§6.2）。`max_mel=100/300` 两种长度下 b=3 都稳定在 5.5 ms/行token，**吞吐 2.6×**。

### 6.1 端到端 A/B（含 s2mel / bigvgan，2026-10-30 实测）

条件：198 字文本 → `max_text_tokens_per_segment=80` 切成 **6 段**，`max_mel_tokens=1500`、`num_beams=3`、`diffusion_steps=25`、四项 fp16 全开、`examples/voice_05.wav`、单配置独立进程（`tools/bench_e2e_batch.py`）：

| `gpt_batch_size` | gpt_gen | s2mel | bigvgan | **总计** | **RTF** | 端到端加速 | gpt 加速 | 显存峰值 | 音频长度 |
|---|---|---|---|---|---|---|---|---|---|
| 0（逐段，基线） | 34.47 s | 7.74 s | 1.11 s | **47.33 s** | 1.1455 | 1.00× | 1.00× | 4.33 GiB | 41.32 s |
| 2 | 20.45 s | — | — | **31.90 s** | 0.8129 | 1.48× | 1.69× | 4.84 GiB | 39.19 s |
| 3 | 17.44 s | 7.61 s | 1.12 s | **30.17 s** | 0.7699 | 1.57× | 1.98× | 5.31 GiB | 39.19 s |
| 4（无护栏，事故） | **291.76 s** | — | — | **301.25 s** | 7.25 | **0.16×（慢 8.5 倍）** | 0.12× | 5.79 GiB | 41.54 s |
| 4（护栏自动降到 3 行，分组与 b=3 完全相同） | 15.33 s | 5.98 s | 0.84 s | **25.28 s** | **0.5974** | **1.87×** | **2.25×** | 5.42 GiB | 42.32 s |
| 4（护栏曾降成 2 行，余量取 1.5GiB 时） | 18.51 s | 5.93 s | 0.84 s | **28.29 s** | 0.6977 | 1.67× | 1.86× | 4.85 GiB | 40.54 s |

（同一配置多次跑的 total 在 25.3~30.2 s 之间波动，取决于每段实际生成多长——`do_sample=True` 是随机的；RTF 已按各自音频长度归一化。**上表每一行都只有一个样本，样本噪声 ±10~15%（§6.3），所以 b=3 的 1.57× 和 b=4 的 1.87× 不是配置差异**：被护栏降成 3 行后两者分组完全相同，差的只是运气。**行数不是越多越好**：12 行 beam 会掉进 §6.2 的换页悬崖，9 行是 8G 卡上的甜点。）

两个结论：

1. **GPT 解码占端到端 ~73%**（基线里 34.47/47.33），s2mel 只占 ~16%、bigvgan ~2%。§3 里"s2mel 是大头"的说法来自别的配置，按 `>> gpt_gen_time / s2mel_time / bigvgan_time` 那四行重新以本节为准。
2. **段级批处理是这一轮唯一稳的端到端收益**：47.33 → 25.3~30.2 s（多次样本），RTF 1.15 → 0.60~0.77，从"比实时慢"变成"比实时快 1.3~1.7 倍"。

### 6.2 显存悬崖：b=4 在 1500 token 上会慢 8 倍（已加护栏）

同配置 `gpt_batch_size=4` 不加护栏时：`gpt_gen 291.76 s`、总 301.25 s、RTF 7.25 —— 比基线**慢 8.5 倍**。而且**没有任何截断告警**，每行都正常在 EOS 停下（音频 41.54 s 正常），说明不是"某行跑飞"，纯粹是每步太慢（≈373 ms/步，平时 23 ms/步）。

原因：批处理的 cache 是 `行数 × beam 数` 条，`4 行 × 3 beam × 1500 token × 120 KB = 2.16 GB`，每步 `torch.cat` 都要重建一遍这个体量，触到 8G 卡在 Windows 上的显存换页。同一配置把 `max_mel` 降到 400（cache 只 0.58 GB）就恢复到 18 ms/步、13 s 跑完 —— 是**长度 × 行数**一起把显存顶爆，不是行数本身。

所以 `_precompute_segment_codes` 开头按预算反推最大行数并**自动降级**：

```python
# KV 每条每 token = n_layer × 2(K,V) × n_embd × 2B(fp16) = 24×2×1280×2 = 122880 B
_bytes_per_row = self._kv_bytes_per_token() * max_generate_length * num_beams
_max_rows = max(1, int(self._gpt_batch_budget_bytes() // _bytes_per_row))
```

预算默认**自适应**（`gpt_batch_max_gib=0`）：`free = torch.cuda.mem_get_info()` 减去 1.0 GiB 安全余量。8G 卡预生成前实测 `free=2.64GiB` → 预算 1.64 GiB → `num_beams=3`+`max_mel=1500` 时算出 3 行，正好是实测最优且安全的配置；6G 卡会退化成 1 行（等于不批处理）；16G/24G 上不再受这个约束，由 `gpt_batch_size` 本身决定。传 `gpt_batch_max_gib=固定值` 可手动覆盖（例如想再压 0.5 GiB 给别的服务）。`INDEXTTS_DEBUG_BATCH=1` 能看到 `rows clamped 4 -> 3` 与 `free=2.64GiB` 两行。

**注意 `self.gpt.dtype` 在有非浮点缓存时不可靠**，曾把 fp16 模型算成 4 B/token，护栏放宽一倍、b=4 又退回单行 —— 现在改成扫第一个浮点参数的 dtype。

设计要点（都是踩过的坑）：

1. **只走非流式路径**：流式要一段生成完就出首包，拼批会拖慢首包，`stream_return=True` 时自动退回逐段。
2. **变长 batch 靠 `prepare_gpt_inputs` 的逐行左填充**（`model_v2.py:609-628`）：它先按行剥掉 start/stop token，再按"条件 34 帧 + 本行文本 + 2"左填充并对 pad 位把 `attention_mask` 置 0。所以**不能假设 prefill 时 batch 内同长**，也不要把 pad 位算进文本长度。
3. **cond / emo / emovec / cond_lengths 都要按 b 行给**：`inference_speech` 内部 `torch.cat` 要求 batch 维一致（`model_v2.py:682`），否则报 `Sizes of tensors must match except in dimension 1`。
4. **按文本长度贪心分组**（`length_ratio=4.0`）：组内所有行必须跑到最慢那行结束，长度太不齐会浪费；但实测每行边际成本只有单行的 ~10~40%，所以只要不是极端不齐，拼批仍然划算。
5. **`emovec` / `speech_conditioning_latent` 提到循环外只算一次**：它们只取决于音色/情感参考音频，与文本无关，原来每段重算一遍（每段都要过一次条件编码器）。

开关：`IndexTTS2(..., gpt_batch_size=4)`，或每次调用传 `generation_kwargs={"gpt_batch_size": 4}`（行数会上限受 `gpt_batch_max_gib=1.75` 约束）。**默认 0 = 关闭**，逐段生成的老行为完全不变。

> 默认值待定：A/B 数字已经出来（b=2 端到端 1.5×，b=3 端到端 1.5~1.6×，§6.3），但 fp16 下批处理会让个别段在第 48 步后采样路径与逐段不同（§5.5，`do_sample=True` 时本就随机）。要不要默认开、默认开几行，等使用方拍板。

验证脚本：`python tools/verify_batch_codes.py --fp32`（期望 `all_equal=true`）——它直接调用生产分支里的 `_precompute_segment_codes`，与逐段生成逐 token 比对。

### 6.3 收益边界：样本噪声、段数与组内均衡（2026-10-31 补测）

**重复样本**（198 字 / 6 段 / `max_text_tokens_per_segment=80`，同机隔天复测，桌面壁纸引擎常驻占用约 1 GiB、30% GPU）：

| 配置 | 总耗时 | gpt_gen | RTF | 峰值显存 |
|---|---|---|---|---|
| b=0 第一次 / 第二次 | 47.33 / 43.40 s | 34.47 / 31.22 s | 1.1455 / 1.1079 | 4.33 / 4.35 GiB |
| b=2 第一次 / 第二次 | 31.90 / 27.54 s | 20.45 / 17.25 s | 0.8129 / 0.6768 | 4.84 / 4.82 GiB |

波动 ±10~15%，来源是 `do_sample=True`（每次生成的音频长度不同）+ 桌面 GPU 占用。**单样本差值小于 15% 不能算配置差异**：b=3 的 gpt 17.44 s 与被护栏降成 3 行的 b=4 的 15.33 s 分组完全一致，12% 的差就是噪声。按两次均值，**b=2 相对 b=0：端到端 1.5×（45.4 → 29.7 s）、gpt 1.74×、峰值显存只多 0.49 GiB**。

**段数与组内均衡**：一组的成本 ≈ f(k) × 组内最长段，k=2/3/4 时 f = 1.10/1.20/1.30（§6 单步微基准），所以 gpt 阶段加速比 ≈ `Σ段长 ÷ Σ(组内最长段 × f(k))`。用上表文本的真实分组验证：

| 配置 | 分组（段 token 数） | 账面成本 | 预测 gpt 加速 | 实测 gpt 加速 |
|---|---|---|---|---|
| b=0 | 46+80+63+67+57+37 | 350 | 1.00× | 1.00× |
| b=2 | (37,46) (57,63) (67,80) → 1.10×(46+63+80) | 208 | 1.68× | 1.69 / 1.81× |
| b=3 | (37,46,57) (63,67,80) → 1.20×(57+80) | 164 | 2.13× | 1.98× |

**同样的文本切成几段**取决于分段上限（server 默认 120，`tools/bench_e2e_batch.py` 默认 80）：

| 文本字数 | 上限 120 | 上限 80 |
|---|---|---|
| 40 字 | 1 段 [78] | 1 段 [78] |
| 80 字 | 2 段 [81,75] | 3 段 [46,80,30] |
| 120 字 | 3 段 [81,108,35] | 4 段 [46,80,63,35] |
| 198 字 | 4 段 [81,108,104,57] | 6 段 [46,80,63,67,57,37] |

三条硬边界：

1. **单段 = 零收益**。批处理入口是 `_gpt_batch_size > 1 and not stream_return and segments_count > 1`（`infer_v2.py:792`），40 字这类单句请求开关等于没开，用户开了没感觉属正常。
2. **只有非流式**。`stream_return=True` 一律逐段，拼批会拖慢首包。
3. **段多不等于加速大**。加速比由"Σ段长 ÷ (组数 × 组内最长段 × f(k))"决定：均衡的 2 段就能到 1.8×（gpt），折合端到端约 1.35~1.45×；段数多但长短悬殊时，最快那行被最慢那行拖住，`length_ratio=4.0` 只是兜底。所以开关说明应标注"仅非流式、≥2 段生效"。

### 6.4 三档开关实施方案（2026-10-31 定稿并实施）

结论先说：**这一版默认仍是 0（关闭）**，把 `-1` 与手动行数作为可选项暴露出去；等 12G+ 显卡验收过、且使用方接受"开启后输出字节变化"，再把默认翻成 `-1`。不默认开的原因：批处理在 fp16 下会改变个别段的采样路径（§5.5，`do_sample=True` 本就随机），属于"会改成品字节"的选项，不能静默打开。

三档语义：

| 取值 | 名称 | 行为 | 实测/推算 |
|---|---|---|---|
| 0 / 1 | 关 | 逐段生成，旧行为，输出与之前完全一致 | 基线 |
| -1 | 自动（最大加速） | 按当前空闲显存反推行数（`_auto_gpt_batch_size`，上限 12），吃满预算 | 8G → 3 行；6G → 1 行（等于关） |
| 2~12 | 手动行数 | 固定拼这么多段，仍受 `gpt_batch_max_gib` 预算护栏压低 | 2 行：端到端 1.5×、显存 +0.49 GiB（§6.3） |

命名注意："自动"的语义是"吃满预算换最大吞吐"，不是"温和提速"；想"稍快但不吃满"应选手动 2 行（§6.3 的曲线在 2 行处性价比最高，再往上边际收益递减、显存线性涨）。

实施清单（4 项，可分开验收）：

1. **server.py 暴露开关**，直接复用已有的 `model_config.json` 持久化（`_MODEL_CONFIG_KEYS` 在 `server.py:1033`，写入/恢复在 `server.py:1044-1075`）：
   - 加 CLI `--gpt-batch`（默认 0，只作首次启动的初值）；
   - `gpt_batch_size`（必要时连 `gpt_batch_max_gib`）加进 `_MODEL_CONFIG_KEYS`；
   - `state()`（`server.py:317`）返回 `gpt_batch_size`；`set_runtime()`（`server.py:331`）写入 `init_kwargs` 的同时实时同步 `self._tts.gpt_batch_size`，与 `diffusion_steps` 的实时路径一致（`server.py:358-360`）。这样不重启就能 A/B，重启后从 `model_config.json` 恢复。
2. **回报本机实际档位**（现在只有 `INDEXTTS_DEBUG_BATCH=1` 才打印）：在 `_auto_gpt_batch_size` / `_precompute_segment_codes` 里把"本轮实际行数、预算、降级原因"记到实例属性（如 `self.gpt_batch_last = {...}`），由 `/model/state` 透出。没有这一项，用户选"自动"不知道自己吃到 1 行还是 8 行。
3. **前端三档控件**：关 / 自动 / 手动（2~12）。控件旁常驻显示 `本机实际 N 行（预算 X GiB）`、`每行约 +0.5 GiB`、`手动 2 行 ≈ 端到端 1.5×（多段均衡时）`，并标注生效条件"仅非流式、≥2 段；单句请求无变化"（§6.3）。
4. **验收**：
   - 默认 0 时输出 md5 与基线一致（`python tools/verify_batch_codes.py --fp32`，期望 `all_equal=true`）；
   - `-1` / `2` 时不重启切换立即生效，`/model/state` 报的行数与实际 KV 峰值吻合（`torch.cuda.max_memory_allocated`）；
   - 模拟 6G 卡（`gpt_batch_max_gib=0.5`）必须降到 1 行且不报错。

实施结果（2026-10-31）：

- 前端三档文案为「逐段生成 / 自动提速 / 自己定段数」，选中「自己定段数」才展开 2~12 的行数滑轨；标题行右侧常驻本机实际档位（`本机自动 ≈ 3 行（预算 1.63 GiB）`、`每批 3 段，本机可拼 3 行`），并在有历史时追加 `上次：6 段 → 2 批` / `上次：显存不足，退回逐段`。
- 自动模式的行数**跟着本次请求的 `max_mel_tokens` 缩放**：预览按默认 1500 估算（8G 空闲 2.7 GiB → 3 行），实测把 `max_mel_tokens` 降到 400 时同一张卡自动取到 12 行。所以 UI 同时保留"本机预览"和"上次实际"两个数，避免用户以为预览骗人。
- Windows 的 torch 分配器不会把上一轮的缓存块还给驱动：不清缓存时第二次生成读到的 free 会低约 2 GiB，自动模式直接掉成 1 行（`reason=low_vram`）。现在生成开头（拼批前）清一次缓存，`/model` 的预览也带 `refresh`、并有 4 秒缓存（生成中沿用上次空闲值，不去干扰推理）。清完同机 free 从 0.59 GiB 恢复 2.6~2.7 GiB，连续两次自动生成都是 3 行。
- 实机连续验证：手动 2 行（5 段 → 3 批）23.1 s；随后自动两次都正常拼批（无 low_vram），无重启切换立即生效。
- 验收补跑（2026-10-31，`tools/verify_batch_codes.py` 增 `--max-gib`，JSON 增 `gpt_batch_last/peak_delta_mib/kv_est_mib`）：
  - **fp32 严格等价**：`--fp32`（默认 3 段、b=3、max_mel 150）`all_equal=true`，两批分组 2+1；GPT 阶段 4472.5 ms vs 逐段 6003.1 ms（1.34×）。fp16 下 b≥2 仍不逐位相等（采样本就随机 + 填充路径数值差异，§5.5），不是逻辑错，所以只能拿 fp32 做等价门禁。
  - **模拟 6G 卡**：`--max-gib 0.5 --max-mel 1500`、要求 3 行 → 实际 `rows=1, groups=3, budget_gib=0.5, reason=clamped`，不报错，`all_equal=true`。即预算不足一行时护栏退成逐段，不会硬上。
  - **行数 ↔ 显存峰值**：同一组 4 段（文本 token 36/34/34/34，实际生成 208~238 token）跑 b=1/2/3：上报 `groups` 4/2/2、`rows` 1/2/3；`max_memory_allocated` 增量 343.6 / 631.5 / 975.5 MiB，每多一行 +288~344 MiB，线性增长。纯 KV 账（行 × 实际长度 × 122,880 B × 3 beams）是 83.7 / 157.5 / 236.2 MiB，差额来自每步 KV `cat` 的临时副本与 beam 重排（§5.1），说明护栏只按纯 KV 记账是**保守下界**，与 §6.2 的实测峰值一致；上报行数与实际分组、占用方向一致，不是照抄请求值。

不做的事：不新建独立配置文件或第二个开关页；不把行数上限写死成 3；不重测会溢显存的档（b=4 无护栏已有落盘记录 `logs/e2e_bs4.json`，§6.2）。

## 7. 尚未实施的优化方向

1. **CPU 提交开销（最大的一块，b=1 时占 2/3）**：CUDA graph 或算子融合。前提是形状固定：`attention_mask` 长度每步都在变，需要按长度分桶捕获多个图，并让 mask 定长（前向语义上用 -inf 屏蔽未用位置）。采样（`do_sample=True`）的 RNG 也要在捕获范围内处理，风险中等偏高。
2. **`gpt_batch_size` 默认值**：已定（§6.4）：A/B 完成（b=2 端到端 1.5× / gpt 1.74×、显存 +0.49 GiB；b=3 端到端 1.5~1.6× / gpt 2.0×，样本噪声 ±15%），**这一版默认仍为 0**，三档开关（关 / 自动 / 手动 2~12）按 §6.4 实施；等 12G+ 验收且接受字节变化后再把默认翻成 `-1`。
3. **`max_text_tokens_per_segment` 120 → 更大**：减少段数、增加拼批机会，但需联动 `max_mel_tokens` 防截断。
4. **`diffusion_steps` 默认 25 → 10~16**：属音质取舍。端到端占比已经量出来了（§6.1）：s2mel 7.74/47.33 ≈ 16%，砍一半流程步数大约省 8% 总时长，比批处理(1.4~1.6×)小一个量级，所以优先级低。`s2mel_fp16` 已默认开启，仍是最稳的 s2mel 提速项。
5. **静态/预分配 KV cache —— 只在批处理路径上有意义**：`b=1` 时每步 cat 只占 1.3%（§5.1），但 §6.2 显示 `12 行 × 1500 token` 时每步要 cat 2.16 GB，那次 b=4 崩溃的本质就是"拷贝量 ∝ 行数×长度"。如果以后要开更大的 batch（或 fp32、更长文本），预分配定长 KV + 每序列独立 `past_len` 才是解锁点；单条流式路径仍不建议做。

### 已证伪，别再做

| 方案 | 结论 |
|---|---|
| 静态 KV cache（仅为省拼接拷贝） | 拼接只占 1.3%，单独做它没有意义 |
| `num_beams 3→1` 当大杠杆 | 实测 ~12%，瓶颈不在这里 |
| `num_beams` 未重排 → 正确性 bug | 运行时证伪，重排每步都在发生且正确 |
| 关掉 autocast（以为 fp16 cast 拖慢） | 不是迁移点；且混精度权重会直接 `expected scalar type Float but found Half` 崩 |
| `expandable_segments` / 砍 beam 省显存 | 显存不是当前瓶颈（8GB 卡峰值 ~2.9 GiB 跑 b=3） |
| `torch.compile` / flash-attn / tf32 / deepspeed | 见 §2，历史实测均为负优化 |

`inference_cfg_rate` 与分段参数已落地为页面在线可调项，不算待办。

- 两段一批后剩余约 0.35–0.4 GB 全卡余量；开着浏览器、游戏或其它 CUDA 程序时有爆显存风险，退回逐段更稳。
- 批处理只在非流式且 ≥2 段时生效，单段文本零收益（与 §6 一致）。

## 9. 段级字幕与导出耗时（2026-11-02）

字幕不参与推理，也不重新分析音频，只做「记录段边界 → 拼字符串」，因此耗时与 GPU、模型状态无关。

**时间是怎么来的**

- 引擎在**插入段间静音之前**把每段波形的样本数记进 `model.segment_slices`（`indextts/infer_v2.py:_record_segment_slices`）。成品音频 = 各段波形 + `int(sr * interval_ms / 1000)` 的静音，所以字幕起止时间是物理时间，不是按字数比例估算。
- 每次生成顺手写一份 `data/subtitles/<stem>.json`（`version` / `text_source` / `segments`），典型 9 段不到 1 KB；`tmp + os.replace` 原子写，失败只记日志、不影响音频。
- 删音频（历史删除 / 14 天保留期）会连带删 sidecar；启动时再扫一遍孤儿 sidecar。旧音频没有这份缓存，接口回 404，前端整行隐藏。
- 文本用 BPE 词元流锚回用户原文（`difflib.SequenceMatcher`），实测中文 / 英文 / 数字 / 全角标点 100% 保留；失败依次退回 `anchor → proportional → readable`，前端面板标明来源。

**导出耗时（纯格式化，单格式，不含浏览器下载）**

| 字幕条数 | 耗时 |
|---|---|
| 4 | 0.02 ms |
| 50 | 0.16 ms |
| 200 | 0.6 ms |
| 1000 | 3 ms |
| 5000 | 15 ms |

导出接口只读一个小 JSON 再拼字符串，不占推理锁、不碰 GPU；HTTP 与下载本身的开销远大于格式化。实测同一段音频连续导出的端到端延迟在毫秒级，与音频时长无关。

### 10.5 断句粒度 A/B：段数到底值多少（2026-11-08 二测，显存空闲）

第一轮（09:29–09:41）跑的时候显卡已占 7610/8192 MiB，耗时被换页噪声污染、三次非单调，不可用。
这轮在 **315 MiB 空闲**下重测，两轮交错（1,2,3,1,2,3），并新增 `max_sentences_per_segment`
（一段最多装几整句，默认 1 = 原行为）来做同条件对照。`gpt_batch_size` 固定 0。

| 每段句数 | 段数 | 耗时（两轮均值） | RTF | 静音占比 | 0.25–0.35 s 停顿 | 0.5–0.8 s 停顿 |
|---|---|---|---|---|---|---|
| 1（现状） | 17 | **117.67 s** | 1.050 | 24.8% | 16~17 处 | 13 处 |
| 2 | 11 | 111.06 s | 1.001 | 26.7% | 8 处 | 22~25 处 |
| 3 | 9 | **110.05 s** | 0.982 | 27.1% | 5~7 处 | 23~27 处 |

**三个结论：**

1. **段数几乎不影响速度**：17 段 → 9 段只省 6.5%（117.7 → 110.1 s）。原因是 GPT 解码成本正比于**总 token 数**，与切几段无关；段数只带来每段一次的 prefill（~35 ms）和调用开销。**§10.4 里「段数翻倍导致 +23%」的说法作废。**
2. **段内句号的停顿是 0.5~0.8 秒**（`0.5–0.8` 桶：1 句/段 13 处 → 3 句/段 23~27 处），比 `interval_silence=300` 长一倍左右。而 0.25~0.35 桶的条数正好等于「段数 − 1」（16~17 / 8 / 5~7），那就是受控的 300 ms 接缝。
3. **合并让停顿变多、变长**：总静音 20.7 s → 22.5~23.3 s。插入的接缝明明少了 8 处（少 2.4 s），总静音反而多 2 s——因为被合并掉的句号改由模型自己发挥，一停就是 0.6 s 左右。

**所以「一句一段」不是浪费，它买的是「每个句号都停 300 ms、说到做到」。** 想快应该去开批处理（§6，1.4~1.6×），而不是把句子塞回同一段。
